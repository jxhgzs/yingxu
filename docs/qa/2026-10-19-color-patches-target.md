## 可支持的公式判断及边界

对原生 zero 的 8bit RGB 直接检验候选公式，结果另存 `candidate-formula-comparison.json`：

- 亮度 +50 候选 `255*(1-(1-x/255)^3)`，12 灰点最大绝对误差约 2.00 个 8bit 码值。
- 亮度 −50 候选 `255*(1-(1-x/255)^(2/7))`，12 灰点最大绝对误差约 5.18，误差集中近白陡峭区；本组输出形状支持候选，但不能称像素精确相等。
- 去饱和候选固定 luma 权重 `[0.2125,0.7154,0.0721]`，用原生 zero 色块 RGB 算的六点灰值最大绝对误差约 2.27 个码值。

这些只是在父任务静态分析提出的候选上进行运行结果比对，不是从少量点唯一反推出完整闭源公式，也未证明其他值、叠加顺序、HDR、关键帧和其他像素格式一致。高光/阴影的活动参数代际与输出已有实证，其完整公式仍需与静态分析或独立实现逐点对照。

输入 ffprobe 没有 `color_range/color_space/color_transfer/color_primaries` 字段；全部九份原生 MOV 明确 `tv/bt709/bt709/bt709`。灰块 source 与 zero 一致，但有色块 source 与 zero 存在明显差别。调节候选判断应以同一原生 zero 输出作参照，不能把输入颜色解释差异算进调节公式误差。FFmpeg 的最终 8bit 解码值也不等同于原生 GPU 内部浮点纹理值，端点量化后再经过高斜率逆曲线会放大误差。
